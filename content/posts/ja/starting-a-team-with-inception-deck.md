新しいチームが集まったら、まず「何のために集まったのか」と「最初にどこを目指すのか」を話しておきたい。メンバー紹介やタスクの割り振りだけでは、お互いが期待していることまでは見えてきません。

その話し合いに使えるのが、インセプションデッキです。Jonathan Rasmussonが紹介した、プロジェクトの始まりに目的や期待をそろえるための10の問いからなる道具です。原著者の説明は[The Agile Inception Deck](https://agilewarrior.wordpress.com/2010/11/06/the-agile-inception-deck/)で読めます。

ここでは、共通のプロジェクトに取り組む新しいチームを想定して、最初の話し合いの進め方を提案します。時間配分や例は、この記事で考えたものです。

## 初回は、目的と最初の成果を言葉にする

たとえば、問い合わせ対応を改善するために、開発・デザイン・サポートのメンバーが集まったとします。これは架空の例です。

「問い合わせを減らしたい」と言っても、サポート担当は同じ質問への回答を減らしたいのかもしれません。開発担当は不具合を直すことを考え、デザイナーは迷いやすい画面を改善したいと考えているかもしれない。

どれも必要そうですが、最初に取り組むことは変わります。話し合いでは、「減らしたいのはどんな問い合わせ？」「困っているのは誰？」「改善したと言えるのは、何が変わったとき？」まで聞いてみます。

最初の成果は、たとえば「ログインで困る人が、自分で解決方法を見つけられるようにする」。このくらい具体的なら、画面を直すのか、案内を足すのか、まず問い合わせを調べるのかを相談しやすくなります。

## 10の問いを、話す内容の手がかりにする

以下は原著者の10項目を短く言い換えたものです。まず全体を見て、答えが違いそうなところや、まだ答えられないところを探します。

| 話すこと | 確認したいこと |
| --- | --- |
| なぜ取り組むのか | 目的 |
| 短く説明すると何か | 対象と価値 |
| 商品の箱に何を書くか | 利用者への約束 |
| 今回やらないことは何か | 範囲 |
| 誰と協力するか | 関係者 |
| どう実現するか | 解決の方針 |
| 何が心配か | リスク |
| どのくらい大きいか | 規模の見通し |
| 何を優先するか | 制約と調整の余地 |
| 何が必要か | 人・期間・費用 |

たとえば「今回やらないこと」には、問い合わせ改善の例なら「サポート業務全体の自動化は、最初の対象に含めない」と書けます。これで、話している範囲を確認できます。

## 準備では、答えより材料を集めておく

進行役は、依頼の背景、困っている利用者の声、決まっている期限などを共有しておきます。依頼する側と実際に取り組む側が同じ場で話せるようにし、必要なら運用やサポートの担当にも参加してもらいます。

資料には「すでに決まっていること」と「チームで相談したいこと」を分けて書いておきます。予算が決まっているのに変更できる前提で話すと、あとでやり直すことになります。

進行役が書いた案を見せる場合も、たたき台だと伝えます。まだ質問がある人まで、完成した答えに賛成しなくてよいように。

## 初回の90分では、違いを見つけるところまで

初回の相談には、たとえば次の時間配分が考えられます。90分でデッキ全体を完成させる想定ではありません。

| 時間 | 進めること |
| --- | --- |
| 0〜10分 | 集まった背景と、決まっている制約を共有する |
| 10〜20分 | 目的と最初の成果について、各自で書く |
| 20〜45分 | 書いたものを読み、解釈の違いを話す |
| 45〜65分 | 最初に取り組む範囲と、心配なことを話す |
| 65〜80分 | 決めたこと、未決事項、確かめることを整理する |
| 80〜90分 | 誰が何を確認し、いつ再び話すかを決める |

各自で書く時間を先に取るのは、最初に出た意見に引っ張られにくくするためです。ひとりずつ読んでもらい、進行役はすぐに一つの文章へまとめず、違う答えを並べておきます。

![目的と期待を各自で書き、違いを話し、決定と未決事項を分け、次に確認することを決める流れ](/TIL/images/team-kickoff-ja.svg)

議論が広がったら、「その話は今決める必要がある？」「判断するために足りない情報は何？」と聞いて戻します。技術の詳細など、別の場で検討できる話には、確認する人と次に話す日を添えます。

## 意見が分かれたら、その理由を残す

同じ項目に違う答えが出ても、すぐに多数決をする必要はありません。見ている情報や、守りたい条件が違うかもしれません。

たとえば、公開日を優先する意見と、機能をそろえてから公開したい意見が出たら、まず理由を聞きます。前者には外部イベントがあり、後者には利用者への約束があるのかもしれない。理由が分かると、最初の公開範囲を小さくする案なども検討できます。

決めきれないときは、「公開日は固定なのかを依頼者に確認する」のように、次の行動へつなげます。記録には確認する人と日付も必要です。品質について話すなら、個人情報の保護や、必ず通すテストなど、守る条件を具体的にしておきます。

## 日々の働き方も、別に相談しておく

インセプションデッキで話すのは、主にプロジェクトの方向です。新しいチームでは、毎日の進め方も決める必要があります。

たとえば、優先順位を誰が決めるか、困ったときはどこで相談するか、レビューをどう頼むか。完成とする前に誰が何を確かめるかも、最初の仕事を始める前に話しておきたいところです。

まず困りそうなことから短く決めて、実際に働いてから見直します。「急ぎの相談はチャットで声をかけ、決まった内容はタスクにも残す」といった、行動が分かる約束にすると使いやすくなります。

原著者も[チーム立ち上げに関する資料](https://rasmusson.wordpress.com/wp-content/uploads/2008/01/rasmusson-agileinceptiondeckbootcamp.pdf)で、役割やチームの実践について話す場を扱っています。

## 次の仕事を始められる状態にして終える

終わる前に、決めたことを参加者が自分の言葉で説明できるか確かめます。言い方が違っても、対象や最初の成果が同じなら進められます。違いが残るなら、その項目は未決として残します。

記録には、決めたこと、未決事項、次に確認する人と日付を書きます。読むだけで次の行動が分かる形にして、参加できなかった関係者にも共有します。

問い合わせ改善の例なら、最初の仕事は「直近のログインに関する問い合わせを、サポート担当と開発担当で一緒に読む」かもしれません。そこで見つかったことを持ち寄り、次の相談で対象を絞ります。最初に書いた目的や範囲も、その時点の情報に合わせて見直せます。
