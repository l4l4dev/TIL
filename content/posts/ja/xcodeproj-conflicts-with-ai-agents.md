複数のチームで 1 つの `.xcodeproj` を触っていると、リリースの前によく `project.pbxproj` がコンフリクトします。個人で作っている macOS の1日プランナー [FirnPlanner](https://firnplanner.l4l4.dev/) は、プロジェクトファイルを新しい形式に移りました。Xcode 27.2 で入った `project.xcproj` (JSON5) です ([移ったときの記事](/TIL/ja/posts/xcodegen-to-xcproj/))。この形式でコンフリクトは楽になるのかを考えて、あわせて手元のリポジトリで実際に何がぶつかっていたかを数えました。

結論から書くと、楽になる見込みはあります。ただ、効いているのは JSON という形式より「同期フォルダ」の方です。そして AI のエージェントを並行に動かしているこのリポジトリでぶつかっていたのは、プロジェクトファイルでもコードでもなく、作業の記録の方でした。2026 年 10 月 6 日時点の記録です。

## pbxproj がぶつかるのは、1 本のファイルで 4 か所が変わるから

`project.pbxproj` では、ソースファイルを 1 本足すだけで、だいたい次の 4 か所が書き換わります。

- `PBXFileReference` (ファイルそのもの)
- `PBXBuildFile` (ターゲットに入れる印)
- グループの `children` (ナビゲーターでの置き場所)
- ビルドフェーズの `files` (コンパイルする一覧)

それぞれの行は、ランダムな 24 桁の ID で結ばれています。2 つのチームが同じグループに別々のファイルを足すと、どちらも同じ一覧の隣り合う行を書き換えるので、ぶつかります。しかも中身が ID だらけなので、どちらを残せばいいかを人が読んで決めにくい。リリースの前に各チームの枝をまとめて取り込むと、これが何度も起きます。

## 効くのは同期フォルダで、JSON はその次

`project.xcproj` に移ってから、ぶつかり方に効いていると考えているのは 2 つです。

1 つ目は、**同期フォルダ**です。ソースのフォルダをターゲットに結び付けておくと、フォルダに置いたファイルはそのままターゲットに入ります。ファイルを足す・消す・名前を変えるときに、プロジェクトファイルが変わりません。上の 4 か所がそもそも書き換わらないので、いちばん効きます。ただし同期フォルダは Xcode 16 から `project.pbxproj` でも使えます。JSON に移らなくても、ここは取り入れられます。

2 つ目が、**JSON5 という形式**です。

```json5
{ "kind": "folder", "path": "MobileTests", "target-membership": [ "FirnPlannerMobileTests" ] },
```

ID ではなくパスとターゲットの名前で書かれているので、ぶつかっても、何と何がぶつかったのかが読めます。末尾のカンマも許されるので、配列の最後に 1 行足しても、前の行が変わりません。隣の行と同時に書き換えてぶつかる場面が減るはずです。

ぶつかり得るものは残っています。ビルド設定、ターゲットの追加、パッケージの依存、フォルダの例外 (別のターゲットと共有するファイル) は、今も `project.xcproj` に書かれます。もう 1 つ、開いている Xcode がプロジェクトファイルを自分の形に保存し直すことがあります ([前の記事](/TIL/ja/posts/xcodegen-to-xcproj/)の後半)。チームで Xcode の版がそろっていないと、整形の違いが差分になって、ぶつかる原因になるかもしれません。これはまだ確かめていない心配です。

## 660 件のマージをやり直して、何がぶつかっていたかを数えた

FirnPlanner の開発リポジトリでは、実装の大半を AI のコーディングエージェント (Claude Code) に任せています。エージェントは git worktree ごとに並行で動きます。2026 年 8 月 1 日から 10 月 6 日までの main には、マージコミットが 660 件あります。

git はコンフリクトそのものを記録しません。そこで、マージコミットの 2 つの親を `git merge-tree` でもう一度マージし直して、ぶつかったファイルを出しました。

```sh
git rev-list --merges main | while read m; do
  git merge-tree --write-tree --name-only --no-messages "$m^1" "$m^2" >/dev/null
  [ $? -eq 1 ] && echo "$m"   # 1 はコンフリクトあり
done
```

`--name-only` を付けると、2 行目以降にぶつかったファイルの名前が出ます。結果は次のとおりです。

| 項目 | 数 |
| --- | --- |
| コンフリクトがあったマージ | 126 件 (8 月 19、9 月 86、10 月 1〜6 日 21) |
| そのうち、ぶつかったのが作業の記録だけのマージ | 94 件 |
| 記録とコードの両方 | 11 件 |
| コードなど記録以外だけ | 21 件 |
| ぶつかったファイル: タスクの記録 | 73 |
| ぶつかったファイル: 仕様と確定値の doc | 46 (仕様 29、デザインの確定値 16、ほか 1) |
| ぶつかったファイル: Swift | 38 (23 件のマージ) |
| ぶつかったファイル: スナップショットの PNG | 14 |
| ぶつかったファイル: lint の基準ファイル / 文字列カタログ | 5 / 3 |
| ぶつかったファイル: プロジェクトファイル | 0 |

作業の記録は、タスク管理の [Backlog.md](https://github.com/MrLesk/Backlog.md) のタスクファイルと doc です。エージェントはそれぞれ、自分のタスクファイルに作業の記録を足し、仕様の doc を直します。同じ doc を別々の枝で直すので、ぶつかります。

数え方には限界があります。数えられるのは、マージコミットとして残ったものだけです。fast-forward や、worktree で載せ直した (rebase) ときのコンフリクトは入りません。そこでエージェントのセッションのログに残った `CONFLICT (content): Merge conflict in ...` の表示も数えました。記録が 128、Swift が 48、そのほか (lint の基準ファイル、文字列カタログ、スナップショット) が 46 で、プロジェクトファイルは 2 回だけでした。その 2 回は、XcodeGen をやめた日に、古い main から作業していた枝を載せ直したときのものです。

## プロジェクトファイルの 0 件は、まだ何も言えない

プロジェクトファイルのコンフリクトが 0 件なのは、JSON の効き目ではありません。9 月 29 日までは XcodeGen を使っていて、`.xcodeproj` を git に入れず、毎回 `project.yml` から作っていました。`project.pbxproj` がぶつかる機会がそもそもありません。`project.yml` は 47 回変更されてぶつかっていませんが、これは XcodeGen の効き目です。

`project.xcproj` に移ったのは 9 月 30 日で、それから 10 月 6 日までに変更は 8 回、コンフリクトは 0 件です。同期フォルダにしたのでファイルの追加ではプロジェクトファイルが変わらず、変更そのものが少ない状態です。JSON にしてコンフリクトが減ったと言えるのは、もっと数がたまってからです。

## AI に並行で任せるなら、ぶつかるのは記録の方

数えてみて意外だったのは、Swift のコンフリクトが少なかったことです。660 件のマージのうち、Swift がぶつかったのは 23 件でした。エージェントに仕事を振るときに「同じファイルを触るタスクは同時に振らない」という決まりにしていて、それが効いているのだと思います。ただし、この決まりが無かった場合と比べたわけではないので、推測です。

代わりに、作業の記録がぶつかっていました。エージェントがそれぞれ同じ仕様の doc に追記するからです。コードは振り分けで避けられても、記録は全員が同じ場所に書きます。チームでリリース前にプロジェクトファイルがぶつかっていた話と、形は同じです。全員が書き込む 1 つのファイルがあると、ぶつかります。

チームの `.xcodeproj` のコンフリクトに悩んでいるなら、まず同期フォルダを入れるのが効くと思います。これは `project.pbxproj` のままでもできます。JSON への移行は、ぶつかったときに読めるようになる、という次の段階です。
