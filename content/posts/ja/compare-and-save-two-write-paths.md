個人で作っている macOS の1日プランナー [FirnPlanner](https://firnplanner.l4l4.dev/) では、ユーザーが選んだフォルダの Markdown ファイルを正としています。日付ごとに 1 ファイルで、ユーザーは同じファイルを他のエディタでも開きます。

そのため、保存には「外のエディタで変わっていたら上書きしない」という決まりがあります。この決まりを守る保存が、2 本の書き込み経路の間で追い越しを起こしました。結論は、書き込みの直前に通し番号を見て、古い要求は書かずに戻す形にした、です。

## 読んだ姿のままのときだけ書く

保存は compare-and-save にしています。アプリは、最後にディスクと同期が取れたと分かっている本文 (以下、控え) を持ちます。保存のときにディスクの中身を読み、控えと同じなら書き、違えば何も書きません。違うのは、アプリの外で誰かが書いたときだからです。そのまま書くと、その編集を黙って消します。

この「読む、比べる、書く」は、1 回の呼び出しの中で中断点なく行います。別々の呼び出しに分けると、読んでから書くまでの間に外の編集が入り込めるからです。コードのコメントにも、この理由が書かれています。

このために、保存の関数 `save` は async にせず同期のまま残しています。理由はコメントに 2 つあります。

- 終了のときに呼ばれる `applicationShouldTerminate` は、戻る前に書き終える必要がある。async にすると、終了を保留して後から返事をする往復が要る
- 判定と書き込みの間に await が入ると、中断点ができて、比べる意味が消える

ファイルを読む `load` のほうは async です。こちらは起動時にメインスレッドを止めないためです。

## 経路が 2 本あると、古い内容が後から着地する

保存の経路は 2 本あります。

- 打鍵が止まってしばらくしてから走る自動保存。ファイル I/O はメインスレッドの外で行う
- 終了、日付の切り替え、ページを離れるとき、保存先を替えるときの書き切り。メインアクター上で同期に行う

同じファイルへの書き込みは、ファイルごとの鍵で 1 本ずつに並べています。ただ、並べても足りませんでした。自動保存は、書く内容を切り出してから、鍵の順番を待ちます。待っている間に、もっと新しい内容の書き切りが先に書き終えると、順番が回ってきた古い内容が、それを上書きします。

compare-and-save があるので、普通は古い要求の比較で落ちます。落ちない場面は、書き切りの前に編集が元の姿へ戻っているときです。たとえば、ディスクが `A` の状態で、打鍵のあとに `B` を書く要求が待ちに入ります。そのあとユーザーが `A` に戻してアプリを終了すると、書き切りは `A` を書きます。ディスクは `A` のままなので、待っていた古い要求の比較 (`A` のままか) も通り、`B` が着地します。画面は `A` なのに、ファイルは `B` です。コードのコメントにも、この場面が書かれています。

もう 1 つ、配置の情報 (タスクの開始時刻) を持つ別のファイルには、比較そのものがありません。こちらは、並び順だけが古い内容の後着を防ぎます。

## 書く内容を切り出すときに通し番号を採り、書く直前に比べる

追い越しは、通し番号 (Ticket) で防ぎました。

- 書く内容を切り出すのと同じ場所で、通し番号を採る。後で採ると、先に採った要求のほうが新しい内容を持つことになり、追い越しを見分けられない
- 鍵で 1 本に並べた中、つまり書き込みの直前に、自分より大きい番号がすでに書き込みへ入っていないかを見る。入っていれば、書かずに戻る
- 書いたあとの確認では間に合わない。その時点で、ディスクには古い内容が載っている

どちらの経路も同じ台帳から番号を採るので、新しい要求が先に書いたあとで、古い要求が後から書くことはなくなります。番号が防ぐのはこの向きだけで、逆の順番については下の「限界」に書きます。

仕組みだけを取り出した小さな例を書いて動かしました (Swift 6 モード、実際のコードではありません)。

```swift
import Foundation

enum Outcome: Sendable, Equatable {
    case wrote
    case skipped(currentOnDisk: String?)
    case superseded
}

struct Ticket: Sendable {
    let key: String
    let sequence: UInt64
}

/// ファイル 1 つ分の保存先と、通し番号の台帳。
final class Store: @unchecked Sendable {
    private let lock = NSLock()
    private var disk: String?
    private var nextSequence: UInt64 = 0
    private var lastClaimed: UInt64 = 0

    init(disk: String?) { self.disk = disk }

    var onDisk: String? { lock.withLock { disk } }

    /// 書く内容を切り出すのと同じ場所で呼ぶ。
    func ticket() -> Ticket {
        lock.withLock {
            nextSequence += 1
            return Ticket(key: "day", sequence: nextSequence)
        }
    }

    /// 読む -> 比べる -> 書く を、中断点のない 1 回の同期呼び出しにする。
    /// ticket を渡すと、より新しい番号が先に書き込みへ入っていた場合は書かない。
    func saveIfCurrent(_ text: String, ticket: Ticket?, isCurrent: (String?) -> Bool) -> Outcome {
        lock.withLock {
            if let ticket {
                if lastClaimed > ticket.sequence { return .superseded }
                lastClaimed = ticket.sequence
            }
            let current = disk
            guard isCurrent(current) else { return .skipped(currentOnDisk: current) }
            disk = text
            return .wrote
        }
    }
}
```

上の「追い越されるシナリオ」を、番号を使わない場合と使う場合で動かします。

```swift
func run(label: String, useTickets: Bool) async {
    let store = Store(disk: "A")

    // 1. 打鍵が止まった。"B" を切り出して、メインの外で書く順番を待つ。
    let asyncTicket = useTickets ? store.ticket() : nil
    let background = Task.detached { () -> Outcome in
        try? await Task.sleep(for: .milliseconds(100)) // 順番待ちの代わり
        return store.saveIfCurrent("B", ticket: asyncTicket) { $0 == "A" }
    }

    // 2. その間にユーザーが "A" に戻し、アプリを終了する。書き切りは同期で走る。
    try? await Task.sleep(for: .milliseconds(20))
    let syncTicket = useTickets ? store.ticket() : nil
    let flush = store.saveIfCurrent("A", ticket: syncTicket) { $0 == "A" }

    let late = await background.value
    print("[\(label)] flush=\(flush) late=\(late) disk=\(store.onDisk ?? "nil") (screen=A)")
}
```

出力は次のとおりです。

```text
[no ticket] flush=wrote late=wrote disk=B (screen=A)
[ticket   ] flush=wrote late=superseded disk=A (screen=A)
```

番号を使わないと、遅れて着いた `B` が書かれ、ファイルが画面と食い違います。番号を使うと、遅れた要求は `superseded` で戻り、ディスクは `A` のままです。例の中の `Task.sleep` は、鍵の順番待ちを再現するための待ちです。

## 見送りの 2 種類を区別し、追い越された回は何も触らない

保存の結果は 3 つに分けています。

- `wrote`: 判定を通って書いた
- `skipped`: 判定に落ちて書かなかった。ディスクが控えと違うので、外で変わったということ
- `superseded`: より新しい要求が先に書き込みへ入っていたので書かなかった

`skipped` と `superseded` は意味が違うので、後始末も別です。`skipped` では、判定に使ったディスクの中身を呼び出し側へ持ち帰ります。読み直すと、判定した瞬間との間に別の書き込みが割り込める、とコードのコメントにあります。持ち帰った中身で控えを据え直し、画面には、外で変わったことを知らせます。画面の編集は捨てません。

`superseded` では、控えも画面も触りません。新しい要求がすでに据え直しているからです。ここで触ると、外の変更と読み違えて、知らせる帯を誤って出します。

控えを据え直す順番にも、世代 (Generation) を使っています。非同期の結果は、保存を始めた順に届くとは限りません。着いた順で控えを更新すると、古い結果が新しい結果を巻き戻します。世代の順にして、新しい世代のときだけ反映することで、これを避けています。通し番号が「書くかどうか」を決め、世代が「控えをどこまで進めたか」を決める、という分担です。

## 待ちには上限があり、防げるのはプロセスの中だけ

同期の書き切りは、メインスレッドで鍵を待ちます。保存先がネットワーク上にあって返ってこないと、無限に待つ間、終了しようとしたアプリが固まります。そこで待ちに上限を置いています (既定は 5 秒)。超えたら書かずに投げ、「保存できませんでした」の経路に載せます。終了のときは、保存せずに終了することも選べます。

限界は、はっきりしています。

- 通し番号も鍵も、同じプロセスの中の書き込みしか並べられない。外のエディタとの競合は、compare-and-save の受け持ちになる
- compare-and-save も、読んでから書くまでの間は、ファイルシステムの上では別々の操作になる。その間に外のエディタが保存すると、その保存は上書きされる。ファイルロックや `NSFileCoordinator` で塞ぐ手もあるが、どちらも相手のアプリが同じ仕組みに従わないと効かない
- 通し番号が防ぐのは、古い要求が新しい要求のあとから書くことだけ。逆に古い要求が先に書き終えると、新しい要求の比べる相手 (切り出したときの控え) はもう古いので、比較で見送られることがある。この記事の最小例には、アプリ自身の先の書き込みを外の変更と見分ける仕組みは入っていない。比較の条件を緩めて通すと、外の変更を守るという目的が崩れる
- 比較は、控えと同じかどうかしか見ない。ディスクの中身が、たまたま控えと同じ内容へ戻っていれば、通ってしまう

この防御が消したいのは、読み込んでから保存するまでの、人が編集している間の長い窓です。そこは消えていますが、読みと書きの間の小さな隙は残ります。

## 2 本の経路を持つなら、書く内容を切り出すときに順序を決める

自分のアプリに持ち帰れそうなことは、次のとおりです。

- 外で変わりうるファイルは、読んだ姿のままのときだけ書く。読む、比べる、書くを、中断点のない 1 回の呼び出しにする。そのために、保存は同期のまま残す
- 書き込みの経路が 2 本あるなら、ファイルごとの鍵で並べるだけでは足りない。書く内容を切り出す場所で通し番号を採り、書く直前に、より新しい番号が先に入っていないかを見る
- 見送りの理由は区別して返す。外で変わったのか、新しい要求に追い越されたのかで、後始末が逆になる
- 待ちには上限を置き、超えたら失敗として扱う。守れる範囲を、書いておく

追い越しの判定は書く直前に済ませる、というところが、この件でいちばん効いた点です。
